# eXBuilder6 요구정의서(.req.md) 작성 SOP

요구정의서는 화면 생성 파이프라인의 출발점이다: `.req.md` → 스튜디오 "설계 생성" → `.pum.json`(화면설계) → CLX 생성. 요구정의서의 내용이 곧 설계 생성 프롬프트가 되므로, 아래 표기법을 따를수록 의도한 설계가 나온다. PUM 구조 자체는 `eb6-author-pum` 스킬이 다룬다.

## 1. 파일 규약

- 파일명은 **영문** `<screen-name>.req.md`(예: `employee-search.req.md`). 문서 하나가 화면 하나다. (`.req.txt`도 인식되지만 신규 작성은 `.req.md`)
  - 파일명에 한글·공백을 쓰지 않는다. 화면의 한글 이름은 본문 `제목:`에 적는다. 요구정의서의 이름이 그대로 `.pum.json`·`.clx`의 이름이 되고, `.clx` 파일 경로가 곧 App ID(URL)가 되기 때문이다.
  - 표기는 소문자 케밥 케이스(`user-role-assign`)를 기본으로 하되, 프로젝트에 이미 화면 파일 명명 관례가 있으면 그것을 따른다.
- **위치는 사용자가 지정한 디렉토리, 지정이 없으면 소스 루트 `clx-src/` 바로 아래**다. 프로젝트 루트·`.eb6/`·스킬 디렉토리 같은 곳에 두지 않는다. 요구정의서가 놓인 폴더가 이후 `.pum.json`·`.clx`가 짝으로 생기는 폴더이므로, 위치가 곧 화면의 위치다.
- **`AIGEN.req.md`라는 이름은 쓰지 말 것** — 그 이름은 요구정의서가 아니라 화면설계 지침 파일로 예약돼 있다(아래 4절).

## 2. 문서 골격

자유 산문도 이해되지만, 다음 구조화 표기가 생성 정확도를 높인다. 동봉 `template-*.req.md`가 골격이고, `example-employee-search.req.md`가 채워진 예시다.

**동봉 예시는 표기법을 보여주는 견본이지 만들 화면이 아니다.** 제목·설명·섹션·정보 엔티티·필드·액션은 전부 사용자의 요구에서 가져온다. 사용자가 "직원 관리"를 요구하지 않았는데 산출물에 예시의 "직원 관리", "부서·이름·나이·입사일", "주민등록번호·거주지"가 나타나면 예시를 베낀 것이다. 예시와 같은 구성(검색 조건 + 결과 그리드 + 세부 사항)을 빌리더라도 그 안의 값은 요구대로 전부 바꿔 쓴다. 요구에 없는 필드·액션은 예시로 메우지 말고, 필요하면 사용자에게 묻는다.

```
1. 화면 정보
* 제목: 직원 관리
* 설명: 직원을 검색하고 상세 정보를 확인하는 화면입니다.

2. 섹션 목록
[검색 조건]
* 타입: field-set
* 목적: search
* 정보 엔티티: 직원
* 액션: 재검색, 검색(주기능)
* 필드 목록: 부서(필수), 이름(필수), 나이, 입사일
```

`[섹션명]` 블록 하나가 화면의 구역 하나가 된다. 탭 구성은 `타입: compose` + `레이아웃: tab` + `하위 섹션 목록:` 아래 들여쓴 하위 블록으로 적는다 — `template-tabbed-master-detail.req.md` 참조.

## 3. 섹션 블록 ↔ PUM 대응

| 표기 항목 | PUM 속성 | 값 |
| --- | --- | --- |
| 타입 | `type` | field-set · data-grid · media · compose |
| 목적 | `purpose` | field-set: search·create·read·modify / data-grid: **read·modify만** |
| 정보 엔티티 | `subject` | 취급하는 데이터 엔티티 이름(명사) |
| 부제목 / 설명 | `subTitle` / `description` | 선택 |
| 필드 목록 | `fields` | 라벨 나열. `(필수)` 접미 → `required: true` |
| 액션 | `actions` | `(주기능)` → primary, `(위험)` → danger, 표기 없음 → 일반 |
| 레이아웃 / 하위 섹션 목록 | compose의 `layout` / `contents` | 탭·가로 배치 시 |

## 4. 작성 규칙

- **필드의 dataType은 적지 않는다** — 생성기가 프로젝트의 필드 타입 카탈로그(구현지침)와 대조해 추론·정규화한다. 대신 확정된 필드 라벨은 빠짐없이 적는다. 필드 목록을 생략하면 생성기가 임의로 추론해 채운다. 카탈로그는 `pum_list_field_types`(CLI: `.eb6/cli-tools/eb6-pum-list-field-types --project .`)로 조회할 수 있다 — 프로젝트에 어떤 필드 프로토타입(첨부·우편번호 등)이 실재하는지 확인하고 필드 라벨·서술을 그 어휘와 맞물리게 쓰면 추론이 정확해진다. 없는 타입을 전제로 요구를 쓰지 않는다.
- 탭·가로 배치는 명시해야만 만들어진다. 명시가 없으면 구역은 전부 세로로 나열된다.
- 그리드에 페이지 이동이 필요하면 "페이징" 요구를 문장으로 명시한다. 페이지 내비게이터를 필드나 액션으로 적지 않는다.
- 액션에는 눌렀을 때의 구체 동작을 한 줄 덧붙이면 좋다 — 생성된 설계의 개발자 주석(comment)으로 이어진다.
- 여러 화면에 공통인 상시 규칙(용어, 스타일, 공통 액션, 금지사항)은 요구정의서마다 반복하지 말고 지침 파일에 둔다: `AIGEN.md`(모든 AIGen 작업 공통) / `AIGEN.req.md`(화면설계 전용). 요구정의서가 있는 디렉토리부터 조상 디렉토리까지 상속 수집되며, 요구정의서에 가까운 쪽이 우선한다.

## 5. 참조 링크 첨부

본문의 마크다운 링크 `[레이블](상대경로)`는 설계 생성 시 자동으로 펼쳐져 프롬프트에 함께 실린다.

- 이미지 파일 → 참조 이미지로 첨부된다 (참고 자료 취급 — 화면 스크린샷 예시와는 다르다)
- 텍스트·마크다운 파일 → 참조 문서로 첨부된다
- 기존 `.pum.json`·`.clx` 파일 → 참조 설계로 첨부된다
- 워크스페이스 밖 경로·외부 URL은 첨부되지 않는다. 재귀 확장은 없다(깊이 1).
- 경로는 문서 기준 상대경로이고 공백은 `%20`으로 적는다.
- 요구와 무관한 링크를 싣지 않는다 — 링크된 파일은 전부 프롬프트에 실려 비용과 잡음이 된다.
- **용어 출처는 링크로 충분하다**: ERD(`.exerd`)·AS-IS 화면 소스(마이플랫폼 `.xml`, `.clx`)·DDL(`.sql`)을 링크하면 설계 생성 시 그 파일이 용어 출처로 `<화면명>.gen.json` 의 `clx.termSources` 에 자동 기록되어 CLX 생성의 코드명 단계에 적용된다. 본문에 "용어의 기준으로 삼아라"는 문장이나 물리명·표기 규칙(대문자 스네이크 등)을 적지 않는다 — 그런 문장은 설계 생성에 섞여 필드 라벨을 물리명으로 오염시킨다. 특정 필드의 물리명을 지정하려면 gen.json 의 manual 항목에 적는다(eb6-author-pum 참조).

## 6. 기존 pum.json에서 역산할 때

이미 있는 `.pum.json`을 요구정의서로 문서화하려면: 구역 순서대로 `[구역 title]` 블록을 만들고, `type`·`purpose`·`subject`를 3절 표의 표기로 그대로 옮긴 뒤, `fields`의 label을 필드 목록으로(`required: true` → `(필수)`), `actions`를 kind 표기로 옮긴다. 동봉 `example-employee-search.req.md`가 `eb6-author-pum` 스킬의 `example-search-master-detail.pum.json`을 역산한 짝이다.

## 7. 마치기 전 점검

- 파일이 사용자가 지정한 디렉토리(지정 없으면 `clx-src/`)에 영문 이름 `<screen-name>.req.md`로 있는가. 파일명에 한글이 있으면 영문으로 바꾼다.
- 제목·정보 엔티티·필드 목록·액션이 사용자의 요구와 일치하는가. 동봉 예시(`직원 관리`)의 값이 남아 있으면 요구대로 다시 쓴다.
- 필드에 dataType·물리명을 적지 않았는가.

## 8. 경계

- 요구정의서 → 설계 생성은 스튜디오에서 수행한다. 이 스킬의 산출물은 `.req.md`까지다.
- 사용자가 명시적으로 요청하지 않는 한 `.pum.json`·CLX 파일을 함께 수정하지 않는다.
